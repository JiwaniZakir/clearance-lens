### D-001 — 2026-11-11 — Disable Next.js 16 Cache Components
**Decision:** Leave `cacheComponents` and `partialPrefetching` **off** in `next.config.ts` (both default off; `partialPrefetching` cannot even be enabled without `cacheComponents`). Use conventional `fetch(url, { next: { revalidate } })` caching for the Speedrun API client instead of `"use cache"`/`cacheLife`.
**Why:** Next 16's Cache Components is a large, still-settling paradigm shift (confirmed via `node_modules/next/dist/docs/01-app/02-guides/migrating-to-cache-components.md`). Every route in this app is either a dynamic MCP/API endpoint (no benefit from static prerendering — POST handlers are never cached regardless) or a playground page whose data is fetched client-side. Adopting the new directive across 11 tool routes + the MCP transport route for zero user-facing gain adds real risk to a judged production deliverable. Conventional fetch caching is stable, documented, and sufficient.
**Impact:** None on functionality or the judging rubric. Revisit only if a future iteration adds genuinely static, cacheable marketing content that would benefit from prerendering.

### D-005 — 2026-11-11 — PII guard ordering nuance between the MCP and API transports (verified live, not just reasoned about)
**Finding:** Ran a real `@modelcontextprotocol/client` against the local `/mcp` route (not just unit tests). Confirmed: (1) full handshake, `tools/list`, `resources/list`, and `tools/call` all work against `@modelcontextprotocol/server` v2 via `mcp-handler`. (2) PII placed in a **declared** schema field (e.g. `explain_rule`'s `topic: "my ssn is 123-45-6789"`) is correctly rejected with the friendly `assertNoPiiCui` message — confirmed live, `isError: true`. (3) PII placed in an **undeclared** extra field is silently stripped by the SDK's own zod validation *before* our `callTool` wrapper (and therefore our PII guard) ever runs — the call just succeeds using the valid declared fields, as if the extra field was never sent.
**Why this is acceptable, not a gap:** The undeclared-field case can never influence output, get stored, or get echoed anywhere — it's a pure no-op, functionally identical to the field never being sent. The hard constraint is about PII never being *processed*; it isn't. The one path where PII could matter — a real, declared, user-filled field — is caught on both transports (the API route's `callTool` sees the fully raw JSON body before any stripping, so it's even stricter on this specific edge case, but the gap it closes is a no-op anyway).
**Action:** Red-team testing (spec §5) will explicitly include both cases as regression tests, so this stays a documented, verified, deliberate behavior rather than an unexamined asymmetry.

### D-009 — 2026-11-11 — JIT research pass: Hard Constraint #4's bias/compliance-law citations independently verified (closes PLAN.md backlog #11)
**Context:** Per D-007 and PLAN.md backlog item #11, none of R1–R5 had independently verified the six hiring-bias-compliance-law citations the original build brief's Hard Constraint #4 leans on (Title VII disparate impact, NYC Local Law 144, Illinois's AI notice law, Colorado's AI Act, EU AI Act high-risk-hiring classification, and *Mobley v. Workday*'s procedural status). Ran the just-in-time research pass PLAN.md called for, using WebSearch (extended mode) and WebFetch against primary/authoritative sources — AgentMux's `search_offerings` was checked first per the standing tool-use policy, returned `gateway-unavailable`, so native web tools were used directly as the policy permits. Full findings, per-item sources, and caveats are in `research/jit/bias-compliance-law.md` (verification date 2026-11-11 throughout).
**Findings (summary — see the file for full sourcing):**
1. **Title VII disparate impact** — still valid, current federal statutory law (42 U.S.C. § 2000e-2(k), confirmed via Cornell LII), never repealed or overturned. But the EEOC's own May 2023 technical guidance applying this doctrine to algorithmic/AI hiring tools was removed from eeoc.gov in January 2025 (confirmed: the live URL now 404s; an archived copy confirms it existed and what it said), and an April 23, 2025 executive order (E.O. 14281, confirmed via the Federal Register/govinfo.gov) directed federal agencies to deprioritize disparate-impact enforcement — which the EEOC's own June 2026 National Enforcement Plan has since done. The theory remains fully available to private plaintiffs regardless of EEOC posture (it's exactly what's proceeding in Mobley, item 6) — but copy should not imply active EEOC enforcement or cite EEOC's AI guidance as currently published.
2. **NYC Local Law 144** — confirmed directly via nyc.gov/DCWP: still in force, unchanged since Jan 2023 (enforcement since Jul 5, 2023); bias audit within 1 year + public results + 10-business-day candidate notice. Lowest-risk citation of the six.
3. **Illinois's AI notice law** — is Public Act 103-0804 (from HB 3773), amending the Illinois Human Rights Act, effective January 1, 2026; prohibits AI-driven discrimination and zip-code-as-proxy, requires employee notice of AI use. **Caveat:** ilga.gov could not be directly fetched this pass (TLS/certificate errors, not a content issue) and a legiscan.com mirror 403'd; the above is corroborated by multiple independent, consistent secondary sources (SHRM, several law-firm client alerts) rather than a direct read of the statute text — flagged as a follow-up, not silently treated as fully primary-verified.
4. **Colorado's AI Act** — confirmed via leg.colorado.gov: the original SB 24-205 never took effect. Its effective date was delayed once (Feb 1, 2026 → Jun 30, 2026, via SB 25B-004, Aug 2025 special session), then — after xAI sued in federal court (Apr 9, 2026) on constitutional grounds and DOJ joined that suit (Apr 24, 2026) — Colorado repealed SB 24-205 outright and reenacted a narrower replacement, SB 26-189 (signed May 14, 2026; regulates "automated decision-making technology" in "consequential decisions," effective Jan 1, 2027). Secondary reporting expects both xAI and DOJ to challenge SB 26-189 too. **Flagged as the least durable of the six citations** — this area has changed three-plus times in 15 months; needs a freshness recheck close to ship, not a one-time citation.
5. **EU AI Act** — confirmed via the European Commission's own AI Act Service Desk and its digital-strategy site: Annex III point 4(a)/(b) does classify recruitment/selection and work-related-decision AI as high-risk (unchanged). The compliance deadline, however, was delayed from Aug 2, 2026 to **Dec 2, 2027** by the "Digital Omnibus on AI" (Regulation (EU) 2026/1744, in force Jul 27, 2026). Any copy citing an Aug 2026 deadline is now stale. (eur-lex.europa.eu itself could not be rendered by the fetch tool this pass — relied on the Commission's own two official pages instead, cross-checked against top-tier law-firm reporting.)
6. ***Mobley v. Workday*** — confirmed active and unsettled via the court docket (PacerMonitor mirror of N.D. Cal. No. 3:23-cv-00770-RFL, entries through Oct 7, 2026) plus Law360/Bloomberg Law reporting: disparate-impact claims proceed against Workday as an HR-vendor "agent" (not just the hiring employer, since Jul 2024); nationwide ADEA collective preliminarily certified (May 2025, expanded Jul 2025); a Jun 22, 2026 ruling let new FEHA gender/age claims proceed while dismissing an improperly-added race claim; discovery disputes ongoing as of Oct 2026. No settlement reported as of this pass.
**Decision:** Backlog item #11 is closed — not by deciding the product's legal framing, but by producing verified, sourced citations that any future UI copy, `explain_rule` content, or `/sources` entry naming these six items must use instead of the brief's unverified originals. Items 2, 5, and 6 were confirmed directly against primary/authoritative sources and are lower-risk to use as-is. Item 1 needs careful wording so the product doesn't overstate current EEOC enforcement posture. Item 3 needs a follow-up direct primary-source read (ilga.gov) before being quoted verbatim, though its facts are well-corroborated. Item 4 is explicitly flagged as unstable and should be re-verified again if there's a meaningful gap before it ships in product copy.
**Impact:** `research/jit/bias-compliance-law.md` added as the sourced reference for Hard Constraint #4's legal framing. No product code, UI copy, or `data/*.json` content was changed in this pass — this was research only, matching the backlog item's own scope.

### D-010 — 2026-11-11 — Link-check script built, debugged, and run to a stable result (1 known, explained, non-blocking exception)
**Context:** spec §5 requires every source URL across `data/*.json` and `research/*.md` to return 2xx/3xx. Built `scripts/linkcheck.ts`.
**Bug found and fixed before trusting any result:** the first version used Node's native `fetch` with a hand-rolled concurrency pool and reported ~90 failures as "aborted." Spot-checked several flagged URLs directly with plain `curl` and they responded correctly in under 300ms — the failures were a bug in the checker (the `fetch`/`AbortController` timers were firing under concurrent load before requests actually completed), not dead links. Rewrote the script to shell out to `curl` per URL instead, which has no such issue.
**Classification decisions, each verified against real responses, not assumed:** (1) a handful of cited URLs are literal API/MCP endpoints (`mcp.speedrun-talent-network.com/mcp`, `mcp.stripe.com`, `mcp.linear.app/mcp`, and our own future `clearance-lens.vercel.app/mcp`) that correctly return 401/405 to a bare unauthenticated GET — this proves the endpoint is live, not dead, so these are classified `WARN` with an explanatory reason, not `FAIL`. (2) Several well-known sites (Glassdoor, W3C, npmjs, ResearchGate, DOI redirectors, `.mil` domains, PACER) return 403/406/419/429 to any automated client regardless of liveness — also `WARN`. (3) Two "URLs" extracted from `research/R1-leverage.md`'s prose (`api.ashbyhq.com/.../{boardName}`, `api.lever.co/.../{site}`) were literal API-pattern examples with unencoded `{...}` placeholders, not real resolvable links — the extractor now filters out any match containing `{`/`}`. (4) Running the check repeatedly in a short window was observed to self-inflict rate-limiting from sites like Reddit/X/HN — added a 3-attempt retry with backoff before classifying a repeat-offender code as `WARN` rather than treating a single rate-limited response as ground truth.
**Final, stable result:** 128 PASS, 44 WARN (all individually explained above), 1 FAIL: `https://mcp.linear.app/sse`, cited only in `research/R2-design-system.md §1.12` as an install-UI-pattern reference — and that report's own text already states *"Linear appears to be mid-migration from SSE to HTTP transport... this report only extracts the install UI pattern, not the specific URL."* This URL does not feed `data/*.json`, any tool, or any shipped UI copy — it is a research citation about a third party's API that changed after R2 was written, exactly the kind of drift R2 itself anticipated and hedged. Left failing rather than special-cased to force a pass, since that would be gaming the check rather than reporting an honest external fact.
**Impact:** `pnpm linkcheck` wired into `npm run verify`; this one exception is a known, accepted, documented state, not an oversight.

### D-012 — 2026-11-11 — `/mcp` had no CORS headers at all — found live, fixed
**Finding:** While doing a final production-readiness pass (independent of the parallel red-team/UI agents), ran `curl -X OPTIONS` and `curl -X POST` with an `Origin` header directly against the running `/mcp` route and found **no `Access-Control-Allow-Origin` header on either response** — confirmed via context7 docs that `mcp-handler`'s `createMcpHandler` does not add CORS headers to its main endpoint by default; its only built-in CORS helper (`metadataCorsOptionsRequestHandler`) is for a separate OAuth protected-resource metadata route this server doesn't use. Every prior smoke test of `/mcp` (dozens, across this build) used `@modelcontextprotocol/client`'s `StreamableHTTPClientTransport`, a Node HTTP client — CORS is a browser-only enforcement, so none of those tests could have caught this; only a real cross-origin browser request would hit it, which is exactly the "MCP client operating in a web browser" case spec §3.3 ("CORS correct for MCP clients") calls out.
**Decision:** `app/mcp/route.ts` now wraps the handler's `GET`/`POST` responses and adds an explicit `OPTIONS` export, all setting `Access-Control-Allow-Origin: *`, `Access-Control-Allow-Methods: GET, POST, OPTIONS`, and `Access-Control-Allow-Headers` including `Mcp-Session-Id`/`Mcp-Protocol-Version`/`Last-Event-ID` (the transport's own session/protocol headers, confirmed needed via R1's research). The wrapper reconstructs the `Response` with the original `body`/`status`/`statusText` so the streaming (`text/event-stream`) transport is preserved, not buffered — verified live (the POST response still carries `content-type: text/event-stream` and chunked transfer-encoding after wrapping) and via the full protocol conformance suite (13/13 still passing).
**Impact:** `tests/protocol/mcp-conformance.test.ts` now asserts the CORS headers on both the preflight and an actual cross-origin POST, so this can't silently regress.

### D-013 — 2026-11-11 — Red-team pass (spec §5): 5 confirmed live PII-guard bypasses fixed in `lib/guard/pii.ts`; ITAR/score/rank/demographic/invented-stat categories held
**Context:** Ran the spec §5 red-team mandate against the live server on both surfaces (`curl` against `/api/tools/*`, and a real `@modelcontextprotocol/client` `StreamableHTTPClientTransport` against `/mcp`) — not unit tests of a mock, actual requests against the running dev server, log file (`/private/tmp/clearance-lens-dev.log`) inspected directly afterward.
**PII/CUI category — 5 real bypasses found and fixed, all independently confirmed via a standalone script calling `scanValueForPiiCui` directly before touching any code, then re-confirmed live post-fix via both `/api/tools/*` and `/mcp`:**
1. **Unicode lookalikes.** Zero-width characters spliced into a digit run (`123​-45-6789`), full-width digits (`１２３-...`), and Unicode dash lookalikes not covered by NFKC normalization (HYPHEN U+2010, NON-BREAKING HYPHEN U+2011, EN DASH U+2013, MINUS SIGN U+2212 — verified directly that NFKC folds FULLWIDTH HYPHEN-MINUS U+FF0D to ASCII `-` but does NOT fold these, since Unicode treats them as semantically distinct) all evaded `SSN_DASHED`/`BARE_9_DIGITS` entirely. Fix: `normalizeForScan()` (NFKC + strip zero-width chars + fold dash lookalikes) runs before every detector.
2. **Base64-encoded PII.** A short base64 blob (e.g. `Buffer.from("my ssn is 123-45-6789").toString("base64")`, 28 chars) with no cleartext keyword and well under `LONG_BASE64_RUN`'s 200-char threshold evaded every category entirely. Fix: extract embedded base64-alphabet tokens (≥12 chars) and decode-and-rescan each, gated by a round-trip re-encode check (rejects anything that isn't truly base64) AND a printable-ASCII-only check on the decoded bytes — verified against realistic non-PII tokens (role-id-shaped, GitHub-username-shaped, long run-on sentences, repeated-letter runs, plain digit runs) producing zero false decodes.
3. **ROT13'd trigger keyword.** `"ssn"` → `"ffa"` (keeping the rest of the sentence in plain English) defeated the keyword-gated bare-9-digit check (`SSN_CONTEXT && BARE_9_DIGITS`) since digits/punctuation pass through ROT13 unchanged but the literal keyword the regex looks for doesn't survive. Fix: also scan `rot13(normalizedText)` and merge findings (ROT13 is self-inverse, so this also still catches a fully-ROT13'd sentence, which already worked before this fix since the dashed-SSN shape itself survives ROT13 untouched).
4. **Percent-encoding the PII itself**, not just surrounding spaces (`%31%32%33-%34%35-%36%37%38%39`), including double-encoding (`%2531...`). Fix: bounded iterative `decodeURIComponent` (3 passes), re-scanning at each stage.
5. **Recursive-scan depth limit (8) failed OPEN, not closed.** `scanValueForPiiCui` silently returned `[]` — treating it as "no PII found" — for anything nested past depth 8, confirmed live via 9+ levels of array/object nesting. This directly contradicts this file's own stated design principle ("prefer a false positive... over a false negative"). Fix: depth-exceeded now returns a new `unscannable_structure` finding (fails closed) instead of `[]`. No legitimate tool input (all 11 schemas are flat objects/short arrays) comes anywhere near this depth, so this cannot false-positive on real traffic — confirmed by running the full existing suite with zero new failures.
**Verified NOT a regression-worthy gap (confirmed, not assumed):** PII split across sibling fields of one call (e.g. half an SSN in `headline`, half in `notes`) still isn't caught — each field is scanned independently, by design, and no fix for this shipped. See `BLOCKERS.md` B-001: closing this requires a real product tradeoff (demonstrated false-positive cost using a benign `query`+`location` example that would otherwise collide), not a mechanical patch, so it's flagged for a human rather than silently patched. Also confirmed live: `prepare_consented_card` is the only one of the 11 tools that echoes a free-text input field back in its output at all, and it only ever echoes its own `.strict()`-validated schema (an undeclared extra key is rejected with `invalid_input`, confirmed live) — never arbitrary passthrough.
**Re-verified D-005 still holds, unchanged by any of the above:** PII in an *undeclared* field is still a silent no-op on the MCP surface (SDK's own zod parsing strips it before our guard runs — reconfirmed live with both a flat SSN and the 9-level-deep nested payload, both succeeded harmlessly) while the API surface (`/api/tools/*`) sees the full raw body and catches both cases (the flat one always did; the deeply-nested one only catches now, post-fix #5 above, closing what would otherwise have been a silent asymmetry worse than D-005 documented).

### D-044 — 2026-11-12 — CSP keeps `script-src 'unsafe-inline'`: tested the alternatives, documented the tradeoff publicly
**Context:** Round 8's recruiter_user docked a trust point partly because the CSP (added in D-033) allows `'unsafe-inline'`, visible to anyone via `curl -D-`. ### D-045 — 2026-11-12 — Upstream calls get per-request timeouts and one overall search budget
**Context:** A self-run probe of all 16 tools (444 calls through the real `callTool()` pipeline, while round 9 was judging production; local only) found no internal errors, throws, or prototype pollution, but `search_defense_roles` routinely took 10–40s. Timing each phase against the live upstream showed why: pages took 4–6s each and per-job detail fetches had a 5.7s median and 24.7s max — and nothing bounded either. `PAGE_SCAN_DEADLINE_MS` was only checked *between* pages, so it couldn't stop a page already in flight (one failing page measured 33s), and the 25-way detail phase had no limit at all. A network-level failure also escaped `fetchJson` as a raw exception, so the pipeline reported it as a generic internal error instead of "temporarily unavailable."
**Decision:** (1) every attempt carries `AbortSignal.timeout` (6s, or less if the caller's deadline is nearer) — per the bundled Next.js fetch docs a signal opts out of render memoization only, which doesn't apply in route handlers, so the data cache is unaffected; (2) callers can pass an absolute `deadline`, and no attempt or backoff runs past it; no backoff after the final attempt (it only delayed the failure 1–4s); (3) every exhausted path throws a `SpeedrunApiError` (504 when unreachable/too slow), never a raw exception; (4) `search_defense_roles` has one 13s budget: the 8s page scan, then the detail phase gets whatever remains (at least 3s); a later page that runs out of time is reported as "slow upstream", not "upstream error". **A bug found alongside:** a failed detail fetch silently dropped its role while `requirementSignalsCheckedCount` still counted it as checked — it now counts only roles whose signals actually loaded, and the note says how many didn't.
**Also learned:** the upstream sits behind Cloudflare rate limiting (HTTP 429, error 1015, `retry-after` ≈ 10s) — my own 444-call probe tripped it from a single IP. Within a deadline, a 10s `retry-after` now fails fast rather than holding the call open.
**Verified:** against the live upstream, an unfiltered search that took 19.9s took 2.8–5.5s; 5 new unit tests (stalled fetch cut off at the deadline; no backoff into a retry that can't fit; network failure surfaces as an upstream error; signals-checked count; detail-phase deadline).
